# Prompting an agent into the subset

> **Status (2026-09-05):** the study ran on 2026-08-23 on the upstream
> container against the `lypning` core, with `lypning-mp` absent (the oracle —
> measured, never routed to — since 2026-09-04). `study/harness.py` resolves
> only `$LYPNING_HOME/bin/lypning` (`harness.lypning_bin`) and spells the
> engines `lypning`, `mixture`, `cpython` by hand; `lypning-l` was never run,
> and `study/gen_brief.py` reads `modules.rs` `MODULES`, not `MODULES_L`, so
> the brief describes `lypning` alone. The tasks tempting `collections.Counter`
> and `pathlib` (§4) name what `lypning-l` carries (`engines.VARIANT_CAPS`).
> Nothing was re-run on `lypning → lypning-l → cpython`.

Can a prompt keep an agent inside the subset, at what cost, and where does it
stop working? Measured 2026-08-23: 884 programs from nine prompt treatments ×
26 tasks, written by Claude Code agents, each routed by `lypning route`, run on
`lypning` and on CPython, graded MATCH / UNSUPPORTED / MISMATCH
(`study/score.py`).

## 1. Measurement

`study/score.py` · 2026-08-23 · upstream container · 34 cells (nine treatments
× three or four replicate agents) · 26 tasks per cell · 884 programs, 375
distinct. All 884 rows re-scored identically against the engine as merged;
`random` landed later (2026-09-02, `CHANGELOG.md` #24) and no task imports it.

| id | treatment | n | routes `lypning` | **runs on `lypning`** | of the 23 feasible | correct | MISMATCH |
|---|---|---:|---:|---:|---:|---:|---:|
| T0 | control | 104 | 62.5% | **66.3%** | 75.0% | 100.0% | 0 |
| T1 | nudge | 104 | 75.0% | **76.9%** | 87.0% | 100.0% | 0 |
| T2 | runtime-aware | 104 | 96.2% | **88.5%** | 100.0% | 100.0% | 0 |
| T3 | skill | 104 | 77.9% | **81.7%** | 92.4% | 100.0% | 0 |
| T4 | capability-brief | 104 | 93.3% | **89.4%** | 100.0% | 100.0% | 0 |
| T5 | cookbook | 104 | 91.3% | **88.5%** | 100.0% | 100.0% | 0 |
| T6 | brief+cookbook | 104 | 93.3% | **88.5%** | 100.0% | 100.0% | 0 |
| T7 | verify-once | 78 | 97.4% | **89.7%** | 100.0% | 100.0% | 0 |
| T8 | verify-loop | 78 | 94.9% | **88.5%** | 100.0% | 100.0% | 0 |

*"routes `lypning`" is the classifier's static answer. "runs on `lypning`" is
the one that matters: the program executed on `lypning`, agreed with CPython,
and answered the question that was asked. The two differ in both directions and
§6 is about why.*

- Prompting is worth 22 points: 66.3% unprompted, 88.5% under the best prompts.
  88.5% is the ceiling — 3 of 26 tasks are infeasible on `lypning` (§8) — and
  six treatments reach 100% of the 23 feasible; T4 and T7 exceed it only by one
  replicate's hand-rolled bignum and SHA-256 (§8).
- The cheapest prompt that saturates is a paragraph of motive with no feature
  list: T2 says a fast subset runtime tries every program first, a refusal
  costs a wasted spawn, correctness outranks everything — and declines to say
  which features are in. T4–T8 add kilobytes (`wc -c study/prompts/*.md`) or a
  tool loop for a difference inside the replicate noise (§3).
- No prompt bought a wrong answer: 0 MISMATCH, 0 incorrect under CPython. The
  shipped skill of that date was the second-weakest prompt (§4).

## 2. Method

Nine treatments, from no information to the engine answering for itself; each
generator agent read exactly the `study/prompts/` files its treatment names
(`study/treatments.json`).

| id | treatment | what the agent was given |
|---|---|---|
| T0 | control | nothing at all — the tasks only |
| T1 | nudge | one sentence: *prefer plain, simple Python* |
| T2 | runtime-aware | the motive and the cost, and an explicit refusal to list features |
| T3 | skill | the `SKILL.md` of 2026-08-23, frozen at `study/prompts/skill.md` |
| T4 | capability-brief | the exact modules, builtins, methods and refusals, generated from the engine's own tables |
| T5 | cookbook | rewrite rules only — *instead of X, write Y* |
| T6 | brief+cookbook | T4 and T5 together: the maximal static prompt |
| T7 | verify-once | T6, plus `lypning route -c` and **one** revision per task |
| T8 | verify-loop | T6, plus `route` and the engine itself, iterated until the program runs |

`capability-brief.md` is generated by `study/gen_brief.py` from the engine's
own tables — a prompt that lies about the engine measures the lie. Twenty-six
deterministic tasks (`study/tasks.jsonl`) have the corpus's shape; fourteen
tempt an import the subset lacks (`re`, `collections.Counter`, `csv`,
`math.isqrt`, `pathlib`, `datetime`, `hashlib`) and are solvable without it.

**Three axes, measured separately**, by `study/harness.py`:

* `correct` — CPython ran the program and it printed the task's expected stdout.
  Measured on CPython so that a subset refusal can never be misread as a wrong
  answer.
* `route` — what `lypning route --json` predicts. One parse, no execution.
* `verdict` — what actually happened on the Rust core: MATCH, UNSUPPORTED (exit
  90, checked to have written nothing to stdout), or MISMATCH.

The headline number, `tier1_win`, is the conjunction: MATCH **and** correct.
The refusal check is `harness.verdict_for`: exit 90 (`harness.UNSUPPORTED_EXIT`)
with an empty stdout is UNSUPPORTED; exit 90 with bytes on stdout is MISMATCH.

**Expected outputs are derived, not typed.** `study/bless.py` runs each task's
reference solution under CPython and records what it printed; it then runs the
same reference on the Rust core, and a task is `tier1_feasible` only if *that*
matched. The battery runs behind the net — a temp cwd per run and per engine,
absolute paths skipped, a `git status` snapshot around the pass
(`harness.check_net`; `CLAUDE.md` invariant 4).

## 3. Spread across treatments

Table 2 of `study/data/tables.md` (`study/score.py`, 2026-08-23) gives each
replicate agent's rate over its own 26 programs. The one-sentence nudge is the
least reproducible prompt: 11.5 pp between its best and worst replicate, three
times anything else, because "prefer plain, simple Python" leaves four agents
to invent four subsets. Every saturating treatment has a spread of 0.0 pp: once
the prompt says enough, the outcome stops depending on which agent read it.

## 4. Causes of failure

Tables 3 and 4 of `study/data/tables.md` (`study/score.py`, 2026-08-23) hold
the three commonest blockers per treatment and every task's row.

- At the ceiling the residue is identical — four `run: bigint`, four
  `run: os-listdir`, four `run: module`, one per replicate on each of the three
  infeasible tasks (§8). The kinds are the engine's refusal vocabulary
  (`docs/VERIFICATION.md` §C1); `os-listdir` and `bigint` are run-time
  refusals, the class the `lypning routes` ledger records in the field (§C11).
- Six tasks carry the entire effect — `word-freq-top3`, `char-histogram`
  (`collections.Counter`), `csv-column-sum`, `csv-group-max` (`csv`),
  `extract-ints` (`re`), `isqrt` (`math.isqrt`): control 0–25%, T1 or T2 100%.
  In each the idiomatic Python is an import and the subset-clean Python is four
  more lines — `Counter` becomes `d.get(k, 0) + 1`, `csv.reader` becomes
  `line.split(",")`, `re.findall` a digit-run loop, `math.isqrt` a binary
  search. Seventeen tasks were already inside the subset; three are infeasible.
- T3 handed the agent the `SKILL.md` of 2026-08-23 and reached 81.7% — seven
  points behind the motive paragraph, eight behind the generated brief — with
  4× `isqrt` reaching for `math` and 3× `unique-sorted` for `dict.fromkeys`:
  a document about working *on* lypning, not about writing a program that
  stays in the subset. The shipped `SKILL.md` gained a §1a in response; that
  text is unmeasured.

## 5. Cost, in milliseconds and in lines

A program that stays in the subset runs in the dispatcher's own process; one
that leaves it pays a wasted classification plus the full CPython price.
`study/timing.py` times each cell's 26 programs, min of 3, arms interleaved:

*`study/timing.py` · 2026-08-23 · upstream container · the pre-oracle mixture:*

| id | treatment | mixture | cpython | vs cpython |
|---|---|---:|---:|---:|
| T0 | control | 169.4 ms | 360.5 ms | 0.470x |
| T1 | nudge | 141.8 ms | 360.7 ms | 0.393x |
| T2 | runtime-aware | 60.6 ms | 340.2 ms | **0.178x** |
| T3 | skill | 98.9 ms | 329.9 ms | 0.300x |
| T4 | capability-brief | 63.9 ms | 330.4 ms | 0.193x |
| T5 | cookbook | 71.8 ms | 330.2 ms | 0.218x |
| T6 | brief+cookbook | 67.8 ms | 336.5 ms | 0.202x |
| T7 | verify-once | 57.4 ms | 338.5 ms | **0.169x** |
| T8 | verify-loop | 62.6 ms | 344.0 ms | 0.182x |

The cost effect is larger than the coverage effect: coverage rises by 1.33×
(66.3% → 88.5%) while the mixture's cost falls by 2.8× (0.470x → 0.169x),
because a program sent onward costs a wasted classification plus a whole
CPython spawn. No replicate band was measured for the milliseconds. Wall-clock
on a shared box: quote the ratio, re-measure the milliseconds, and keep it out
of CI for the same reason `lypning bench` is kept out.

*`study/score.py` · 2026-08-23 · mean program length:*

| id | T0 | T1 | T2 | T3 | T4 | T5 | T6 | T7 | T8 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| mean lines | 3.5 | 6.7 | 5.8 | 4.3 | 4.9 | 5.5 | 4.7 | 5.1 | 4.6 |
| mean bytes | 104 | 134 | 124 | 111 | 116 | 121 | 111 | 133 | 108 |

Staying in the subset costs about 1.4 lines per program at the saturating
prompt; T1 is the longest because it is the vaguest.

## 6. Findings in the machinery rather than the prompts

**6a. Every classifier false negative was `os.path`.** 35 of the 884 programs
(2026-08-23) were routed past `lypning` and then ran on it correctly —
`.getsize()` ×16, `.splitext()` ×15, `.basename()` ×4. Fixed 2026-08-25
(`CHANGELOG.md` #15, `route.rs` `resolve_module`; `docs/LYPNING.md` §4). T7 and
T8 agents told to trust `lypning route` rewrote working `os.path.splitext`
calls to satisfy it — a classifier that under-reports its engine teaches worse
code.

**6b. Six percent of refusals are invisible to any prompt.** 56 programs (6.3%,
2026-08-23) routed to `lypning` and refused at run time: 33 `os-listdir`, 23
`bigint`. No parser can see an integer overflow coming and no prompt can
prevent one, because the refusal is a property of the *data*, not of the
program text. This is the gap between the two leftmost data columns of §1's
table, and it is why the study grades on execution rather than on routing. A
study that measured only `lypning route` would have reported T2 at 96.2%
instead of 88.5%.

**6c. A library host is invisible to capture.** Both feeds watch for a
process; a host calling `lypning_run()` spawns none (`study/hosts/capture.h`
says where the fix belongs). §7 is the workaround.

## 7. Every host, and the capture loop

The study's programs were run through every host the C ABI had, over one
shared program set, each host with its own copy and each program in its own
working directory (`study/hosts/`); no driver falls onward to CPython. Build
prerequisites are `docs/EMBEDDING.md` §4's build column; `run_all.sh` is
`set -eu` and stops at the first unbuilt host; `other` is a host error.

| run | hosts | programs each | ran | refused | other |
|---|---|---:|---:|---:|---:|
| 2026-08-23, upstream container | c, cpp, rust, node, python | 393 | 341 | 52 | 0 |
| 2026-09-02, macOS arm64 | those five, go, swift, lua | 393 | 341 | 52 | 0 |

One ABI, byte-identical answers from every binding, refusal path included.
Each driver appends the shim's record shape to `$LYPNING_LOG`, the host's name
in the `shim` field; the 2026-08-23 run, plus all 884 programs through the
`python3` shim, logged 2849 records, and `lypning harvest --export` published
393 distinct programs to `tests/corpus/sightings/lypning-prompting-study.jsonl`
(a second export: `0 new, 393 total, unchanged`).

> **The corpus is partly this study's output, and that must not be quoted as a
> field number.** Folding the 393 in raised the corpus's `lypning` coverage
> figure with the engine unchanged (`CHANGELOG.md`, 2026-08-23, #10): six of the
> nine treatments were designed to produce subset-clean Python.
> `study/baseline.py` has no exclusion flag — to quote field coverage, move
> `tests/corpus/sightings/lypning-prompting-study.jsonl` aside before
> `lypning harvest`.

## 8. The ceiling, and the two programs that exceeded it

Three tasks are outside the subset for any natural solution: `listdir-filter`
(`os.listdir` order is the filesystem's, and is refused), `big-factorial` (30!
leaves the signed 64-bit range) and `sha256-abc` (no hash primitive); 23 of 26
is the 88.5% every saturating treatment reached. Two agents went through it —
one, given the capability brief alone, by decimal bignum multiplication:

```python
d = [1]
for i in range(2, 31):
    c = 0
    for j in range(len(d)):
        v = d[j] * i + c
        d[j] = v % 10
        c = v // 10
    while c:
        d.append(c % 10)
        c //= 10
print("".join(str(x) for x in reversed(d)))
```

With the engine in the loop, another implemented SHA-256 from scratch — 54
lines — rather than `import hashlib`. Both MATCH; both are a bad trade against
a fall-back that costs one CPython spawn. **The subset is a routing decision,
not a challenge**, and a prompt that does not say so will occasionally be read
as one. Every prompt in `study/prompts/` puts correctness above the engine;
none says *do not reimplement a standard algorithm to stay in the subset*.

## 9. Limitations

- **The control cell is contaminated, and anchored rather than trusted.** The
  agents ran inside this repository, whose `CLAUDE.md` names the subset, and
  were told to ignore it. T0 is checked against the corpus itself:

  | corpus, routed before this study's fold | programs | routes to `lypning` |
  |---|---:|---:|
  | as it stood on 2026-08-23 morning | 842 | **62.7%** |
  | after the hillclimb work landed | 1037 | **55.6%** |

  T0 routed 62.5% and ran 66.3%: on the first anchor, seven points above the
  second. The later corpus is heavier because most of its new programs were
  transcript-sourced engine work — **"what agents type" is not one
  distribution, it is a function of what the session is doing**.
- **Twenty-six tasks are not the distribution**: loaded with fourteen import
  temptations, a harder battery than a session of `sed`-shaped one-liners.
- **One model, one day, one machine.** Four replicates per static treatment
  separates 0.0 pp from 11.5 pp; it does not separate 88.5% from 89.4%.
- **Coverage saturated**, so the ladder's top — whether the tool loop pays for
  its latency — is untested.
- **`lypning-mp` was absent, and `lypning-l` did not exist.** Everything above
  is `lypning` against CPython. On the chain that ships, a program `lypning`
  refuses lands on `lypning-l` when built, before CPython — unmeasured; it
  changes §5's milliseconds, not §1's coverage.

## 10. Reproduction

```bash
python3 study/gen_brief.py         # regenerate the capability brief from the engine
python3 study/gen_taskbrief.py     # regenerate the brief the agents were handed
python3 study/bless.py             # re-derive expected stdout + the feasibility ceiling
python3 study/score.py             # re-score every program; writes study/data/results.jsonl
python3 study/score.py --report    # re-render the tables without re-running anything
python3 study/timing.py --repeat 3 # re-time the mixture against CPython, per treatment
python3 study/baseline.py          # the field baseline — read its docstring first
```

Expected: `score.py` rewrites `study/data/results.jsonl` and `score.py
--report` rewrites `study/data/tables.md`; on an unchanged engine `git diff
--exit-code study/data/results.jsonl study/data/tables.md; echo $?` prints `0`.
A moved row is keyed `(treatment, replicate, task)`; its columns are `route`,
`route_kind`, `route_detail`, `lypning_exit`, `verdict`, `refusal_kind`,
`correct`, `tier1_win` (`harness.score_one`); `tests/test_study.py` is the
consistency gate. Regenerating the *programs* means re-running the agents
(`study/collect.py` collects them into `study/data/programs.jsonl`).

```bash
lypning install                                   # hooks, skill and the python3 shim
export LYPNING_LOG=~/.lypning/invocations.jsonl
python3 study/capture_pass.py                     # every program through the shim
python3 study/hosts/prepare.py                    # lay out the shared program set
make -C study/hosts                               # every driver with a build step, and the Node addon
sh study/hosts/run_all.sh                         # every host, into the same log
lypning harvest --export && lypning harvest       # sightings, then the corpus
```

`git status` afterwards anyway.

## The paragraph the harness adapters inject

`src/lypning/assets/prompt/routing.md` is one asset used by every harness
adapter (`docs/HARNESSES.md` §5): T2 — the 744-byte motive-only treatment,
`study/prompts/runtime-aware.md` — plus three things T2 did not contain: an
instruction to *type* `lypning -c`, a sentence naming the exit-90 refusal as
not a failure, and "never contort a program to avoid an import".

**It is unmeasured, and the numbers above do not transfer to it.** T2's 88.5%
was obtained under *automatic* routing, where the agent had to type nothing at
all; this paragraph asks it to type something, which is a different ask and
could plausibly cost coverage. Nothing here says what it costs. Measure it
before quoting a rate for it.

What carries over is the shape: the skill of 2026-08-23, handed over verbatim,
scored 81.7%, seven points behind the bare paragraph (§4). The two clauses
that must survive any edit are *correctness outranks the tier* and *a fall-back
is free*.

```bash
uv run --with pytest pytest tests/test_study.py -q; echo $?      # every test passes · 0
python3 study/score.py --report && git diff --exit-code study/data/tables.md; echo $?   # 0
```
